## 1. Overview

Enables the creation and management of secure programmatic access for Dell ObjectScale users by provisioning and controlling S3-compatible access keys.

> **Terraform Reference Resource:** `objectscale_iam_user_access_key`
> **Ansible Module Name:** `dellemc_objectscale_iam_user_access_key`
> **Category:** Identity & Access Management (IAM)

## 2. Functional Requirements

- The module shall manage iam user access key resources on Dell ObjectScale via REST API.
- The module shall support **check_mode** (dry-run) for all operations.
- The module shall use Python client files generated from the ObjectScale OpenAPI specification for REST API access.
- The module shall authenticate using the ObjectScale token-exchange flow (Basic Auth → X-SDS-AUTH-TOKEN).
- The module shall support `state: present` (create/update) and `state: absent` (delete).
- The module shall be idempotent: running twice with the same parameters shall produce no changes on the second run.
- The module shall validate all inputs before making API calls.
- The module shall return meaningful error messages on failure using `exit_json(fail=True, msg=...)` instead of `fail_json()`.
- The module shall follow ansible-objectscale collection coding conventions and directory structure.
- Connection parameters (hostname, username, password, validate_certs, port, timeout) shall be handled via a shared base class or module_utils.

## 5. Supported Operations (CRUD)

### CREATE ✓ Supported
- **API:** `IamServiceCreateAccessKey`
- **Endpoint:** `POST /iam?Action=CreateAccessKey`
- **Parameters:** UserName, XEmcNamespace
- **Verification:** After creation, calls ListAccessKeys to fetch full key metadata and match by AccessKeyId.

### READ ✓ Supported
- **API:** `IamServiceListAccessKeys`
- **Endpoint:** `POST /iam?Action=ListAccessKeys`
- **Parameters:** UserName, XEmcNamespace, Marker, MaxItems
- **Verification:** Lists all keys for user, matches by AccessKeyId to find specific key.

### UPDATE ✓ Supported
- **API:** `IamServiceUpdateAccessKey`
- **Endpoint:** `POST /iam?Action=UpdateAccessKey`
- **Parameters:** AccessKeyId, UserName, Status, XEmcNamespace
- **Verification:** Only status field is updatable (Active/Inactive). Calls ListAccessKeys to refresh state after update.

### DELETE ✓ Supported
- **API:** `IamServiceDeleteAccessKey`
- **Endpoint:** `POST /iam?Action=DeleteAccessKey`
- **Parameters:** AccessKeyId, UserName, XEmcNamespace
- **Verification:** Deletes the specific access key and removes from state.

## 6. API Reference

| HTTP Method | Endpoint | Purpose | Request Parameters | Response |
|-------------|----------|---------|-------------------|----------|
| POST | `/iam?Action=CreateAccessKey` | Create new access key | UserName, XEmcNamespace | IamServiceCreateAccessKeyResponse (AccessKeyId, SecretAccessKey) |
| POST | `/iam?Action=ListAccessKeys` | List access keys for user | UserName, XEmcNamespace, Marker, MaxItems | IamServiceListAccessKeysResponse (AccessKeyMetadata[]) |
| POST | `/iam?Action=UpdateAccessKey` | Update access key status | AccessKeyId, UserName, Status, XEmcNamespace | BasicResponse |
| POST | `/iam?Action=DeleteAccessKey` | Delete access key | AccessKeyId, UserName, XEmcNamespace | BasicResponse |

> **Authentication:** All API calls use `X-SDS-AUTH-TOKEN` header obtained via Basic Auth token exchange at login.
> **Namespace Header:** Multi-tenant operations require `x-emc-namespace` header.
> **Base URL:** `https://{host}:4443`
> **API Version:** 4.0.0 (ObjectScale Management API)

## 7. Idempotency

Create always generates a new key. Update only applies if status differs. Delete is idempotent. The module should check for existing keys before creating.

> **Requirement:** The module MUST be idempotent. Consecutive executions with the same parameters shall not modify the resource and shall return `changed: false`.

## 8. Error Handling

### 8.1 Expected Error Scenarios

| # | Error Scenario | Expected Behavior |
|---|----------------|-------------------|
| 1 | User does not exist in namespace | Module fails with descriptive error message |
| 2 | Access key ID does not exist | Module fails with descriptive error message |
| 3 | Invalid status value (must be Active or Inactive) | Module fails with descriptive error message |
| 4 | Maximum number of access keys reached for user | Module fails with descriptive error message |
| 5 | Permission denied (401 Unauthorized) | Module fails with descriptive error message |

### 8.2 Error Handling Requirements

- The module shall catch API errors (400, 401, 500) and translate them to meaningful Ansible failure messages.
- The module shall use `module.exit_json(fail=True, msg=...)` with descriptive `msg` for all error paths. **NEVER** use `fail_json()`.
- Error messages must be very clear and include: what operation failed, why it failed, and what the user can do to fix it.
- Sensitive data (passwords, secret keys) shall NEVER appear in error messages.
- The module shall log API request/response details at debug level (excluding sensitive fields).

## 11. Diff Mode Support

The module shall support Ansible's `--diff` mode to show changes that will be made or have been made to resources.

### 11.1 Diff Mode Requirements

- The module shall return a `diff` dictionary in the module output when run with `--diff`
- The `diff` dictionary shall contain `before` and `after` keys showing the resource state before and after the change
- **Secret key handling:** Since the API does not return existing secret key values, the secret key field shall:
  - Show as `<REDACTED>` or `<SENSITIVE_VALUE_REMOVED>` in both `before` and `after` when not being created
  - Show as `<NEW_SECRET_KEY_GENERATED>` in `after` when a new key is created
  - Always indicate when a secret key change is applicable (i.e., on create operations)
- All other parameters (status, user_name, namespace) shall show their actual values in the diff
- The diff shall be clear and human-readable

### 11.2 Diff Mode Best Practices

> **Ansible Best Practice:** Diff mode should:
> - Return structured diff data in the `diff` field of the module result
> - Show only meaningful changes, not the entire resource if only one field changed
> - Use consistent formatting for before/after values
> - Handle sensitive data appropriately (redact or mark as changed)
> - Work correctly with both `--check` and regular execution modes
> - Be implemented for all state-changing operations (create, update, delete)

### 11.3 Diff Mode Example Output

```yaml
# Create operation diff
diff:
  before:
    access_key_id: null
    status: null
    secret_access_key: null
  after:
    access_key_id: "AKIA80817B9F1F4C72CB"
    status: "Active"
    secret_access_key: "<NEW_SECRET_KEY_GENERATED>"

# Update operation diff (status change)
diff:
  before:
    access_key_id: "AKIA80817B9F1F4C72CB"
    status: "Active"
    secret_access_key: "<REDACTED>"
  after:
    access_key_id: "AKIA80817B9F1F4C72CB"
    status: "Inactive"
    secret_access_key: "<REDACTED>"

# Delete operation diff
diff:
  before:
    access_key_id: "AKIA80817B9F1F4C72CB"
    status: "Active"
  after:
    access_key_id: null
    status: null
```

### 11.4 Diff Mode Implementation Notes

- The module shall compare current state (from API) with desired state (from parameters)
- Only show fields that are actually changing in the diff
- For create operations, `before` shall show null/empty values
- For delete operations, `after` shall show null/empty values
- The diff shall be returned even in check_mode when `--diff` is used
